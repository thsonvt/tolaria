# Tolaria as a Second Brain UI — Design

*Date: 2026-05-03. Owner: Brian / Le Thanh Son. Status: design, not yet scheduled.*

## Goal

Extend Tolaria from a markdown PKM into a UI for a "second brain": a vault that ingests external content (YouTube, web articles, Medium, Substack, PDFs, PPTs, Gists) and a native chat surface that reasons over it.

Inspirations: Karpathy's LLM council, Vivian's diplomat brain, NanoClaw. The common pattern is *structured personal corpus + AI that reads it*. Tolaria already owns the corpus side; this design adds ingestion at one end and conversation at the other.

## Decisions locked from brainstorm

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | Ingestion and conversation are designed as one coherent system. | The product is the loop, not either half alone. |
| 2 | Captured items store the **full extracted content** in the note body, not just a link + summary. Embeddings come later as a derived sidecar (path B → C). | Honors "filesystem as single source of truth"; preserves offline reasoning. |
| 3 | Hybrid LLM placement: **local model handles ingestion** (summary, tags, transcript cleanup); **cloud BYOK handles conversation**. | Bulk transformation stays private and free; user opts into cloud per conversation. |
| 4 | Capture triggers are layered: in-app paste-URL + drag-drop first, macOS share extension and browser extension later. | Cheapest path that proves the loop. Triggers funnel into the same inbox; later surfaces add reach without changing the data model. |
| 5 | Captured items use a new `Capture` type, not the existing `Note` type. | Captures are content you consumed, not content you wrote. Filtering and inbox-zero workflows benefit from the distinction. Cost: one new file in `vault/type/`. |
| 6 | Conversation surface is a **native chat panel inside Tolaria**, implemented as an MCP client over the existing Tolaria MCP server. Multi-LLM council mode (D) is deferred to phase 3. | One data interface, multiple surfaces. External MCP clients keep working. Council mode is an extension, not a redesign. |

## Architecture

### Data model

A new `Capture` type joins the existing ten in `vault/type/`. Frontmatter conventions:

```yaml
---
type: Capture
source: youtube | substack | medium | gist | web | pdf | pptx
url: https://...
title: ...
author: ...
captured_at: 2026-05-03T22:14:00Z
duration_sec: 2700        # videos only
page_count: 47            # PDFs only
summary: |
  Three-sentence summary generated by the local model.
tags: [llm, agents, ...]  # local-model suggestions, user-editable
---

# Title

## Summary
(LLM-generated, ~200 words)

## Content
(Full extracted text — transcript with timestamps, article body, PDF text, slide bullets.)

## My thoughts
(User annotations. Inline thoughts attach via the existing sidecar mechanism shipped in recent commits.)
```

The thoughts sidecar (`<note>.thoughts.json` per recent commits) attaches to Captures the same way it attaches to article-rendered Notes — no new mechanism.

Original binaries (PDFs, PPTs) live in `vault/attachments/` and are referenced from the Capture note. They are **not** committed via Git LFS in v1; large files are a known issue deferred to a later ADR.

### Ingestion pipeline

```
URL or file → source detector → extractor → local LLM enrichment → Capture note in vault/inbox/
```

**Trigger (v1):** Cmd+N → paste URL or drag file. The command-bar detects whether the input is a URL (and which kind) or a file path (and which extension), then dispatches to the right extractor.

**Per-source extractors:**

| Source | Extractor | Output |
|--------|-----------|--------|
| YouTube | `yt-dlp` for metadata + `youtube-transcript-api`; whisper.cpp fallback if no transcript | Title, channel, duration, transcript with timestamps |
| Substack / Medium / generic web | Readability (Mozilla port) or Mercury Parser | Title, author, body as markdown |
| Gist | GitHub API (no auth needed for public Gists) | Title, author, file contents concatenated |
| PDF | `pdfium` via Tauri sidecar or `pdf-parse` | Page-broken text |
| PPTX | `python-pptx` via sidecar; or LibreOffice convert to PDF then PDF pipeline | Slide-broken text |

**Local LLM enrichment:** an Ollama-compatible HTTP endpoint configurable in settings. The pipeline calls it for: (a) summary generation, (b) tag suggestion, (c) optional transcript cleanup. Default model recommendation in docs: Qwen 2.5 7B for low-spec, Llama 3.3 70B for Apple Silicon with 64GB+. Tolaria does not bundle Ollama — users install it separately.

**Output:** a new `Capture` note in `vault/inbox/`. The user reviews it, adds their own thoughts, and connects it to projects/topics during the existing weekly Organize phase. No new inbox machinery — Tolaria's inbox is already a derived state.

### Conversation surface

A right-side chat panel in the Tolaria UI, collapsible. Implemented as a **first-class MCP client** that talks to the same Tolaria MCP server external clients use (`mcp__tolaria__search_notes`, `get_note`, `get_vault_context`, etc.).

Key interactions:

- **Free-form chat** — top-level question, AI plans tool calls, streams answer with inline citations.
- **Selection-based ask** — highlight a passage in any note, hit a hotkey, ask a question about that selection. The selection becomes pinned context for the conversation.
- **Citations are clickable** — every reference to a vault note in the AI's answer is a link that opens the note (uses the existing `open_note` MCP tool).
- **Capture-aware** — the AI knows which notes are Captures vs Notes vs Projects, and can answer "what did I read about X?" by filtering on `type: Capture`.

**Provider model:** BYOK to one provider at a time in v1 (start with Anthropic, add OpenAI and Google as the abstraction matures). Keys live in the OS keychain via Tauri's secure storage. No Tolaria-operated server in the middle — the request goes from the app directly to the provider.

**Tool-calling loop:** the chat panel orchestrates the standard agentic loop (LLM emits tool call → run tool → feed result back → repeat). Tools available are exactly the existing MCP tools, plus a small set of new ones (see below).

### MCP server extensions

Existing tools work as-is. A few additions make the surface complete:

- `get_capture_content(note_path)` — returns just the `## Content` section, useful when the AI wants the transcript without the summary or thoughts.
- `find_thoughts_for(note_path)` — returns all sidecar thoughts attached to a note.
- `add_thought(note_path, anchor, text)` — lets the AI propose an annotation; the user approves before it's written.

The third tool is deliberately gated on user approval — an AI agent should never silently mutate the vault.

### Local model dependency

Tolaria detects whether an Ollama endpoint is reachable on startup. If not, ingestion still works but skips the enrichment step (no summary, no tags) — the Capture is created with raw extracted content only, and a banner suggests installing Ollama.

This keeps the app usable without local AI while making the upgrade obvious. Conversation is BYOK to a cloud provider regardless.

## Phasing

| Phase | Scope | Done when |
|-------|-------|-----------|
| **0 — proof of shape** | `Capture` type definition. Paste-URL → web article only (Readability). No LLM enrichment. | A user can paste a Substack URL and get a usable Capture note in inbox. |
| **1 — usable loop** | YouTube + PDF extractors. Local LLM enrichment (summary + tags). Native chat panel with Anthropic provider, no streaming, no citations. | A user can capture a video, then ask the AI "what did this video say about X?" and get an answer that references the transcript. |
| **2 — magical interactions** | Streaming responses. Clickable citations. Selection-based ask. Substack / Medium / Gist extractors. | The chat panel feels native to Tolaria — questions about specific passages work without copy-paste. |
| **3 — extensions** | Embeddings sidecar layer. Multi-LLM council mode. macOS share extension. Browser extension. PPTX extractor. | Captures from anywhere; conversation across the whole vault scales past trivial keyword search. |

Phase 0 is one weekend. Phase 1 is the meaningful first milestone; everything before is plumbing.

## Non-goals (v1)

- **Multi-LLM council mode.** Deferred to phase 3.
- **Browser extension.** Deferred to phase 3.
- **Mobile capture.** Out of scope until a Tolaria mobile build exists.
- **RAG / embeddings.** Deferred until single-context chat over named notes proves insufficient.
- **Cloud sync of attachments.** Binaries stay local; Git size discussion deferred to a separate ADR.
- **Ollama bundling.** Users install Ollama themselves.

## Open questions to resolve before phase 1

1. Do PDF/PPT binaries live in `vault/attachments/` (committed) or `vault/.cache/attachments/` (gitignored)? Affects vault portability vs Git size. Likely an ADR.
2. Does the existing thoughts sidecar mechanism need any change to attach to Captures, or does it work as-is when the underlying note is type `Capture` instead of type `Note`?
3. What is the precise format for transcript timestamps? `[00:12:34] text...` is human-readable but not machine-parseable for clickable seek. Likely a hidden frontmatter index.
4. Does the chat panel persist conversation history? Where? (Probably yes, in `vault/.tolaria/conversations/` as JSON, gitignored.)
5. How does the AI handle a vault with thousands of Captures and no embeddings? `search_notes` is the only retrieval tool today. Phase 1 may need a smarter `search_notes` even before embeddings ship.

## Risks

- **Local LLM quality is the gate on ingestion UX.** A Qwen 7B summary that's wrong half the time is worse than no summary. Mitigation: ship with Llama 3.3 70B as the recommended default for users with the hardware; degrade gracefully when no Ollama is present.
- **Vault size grows fast.** Full transcripts of YouTube videos run ~10–20KB each; a year of heavy use may add hundreds of MB of text. Git handles this but search and editor performance need to scale. Mitigation: profile early in phase 1.
- **MCP tool-calling latency for citations.** Every tool call is a round-trip to the local MCP server. Multi-step plans (search → get → search again) can feel slow. Mitigation: design tool surfaces that return rich enough results in one call.
- **BYOK key handling.** Storing provider keys is not just UX — it's a security surface. Mitigation: Tauri's keychain integration, never log keys, never write them to the vault.
